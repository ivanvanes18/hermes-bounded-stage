# Подключение существующих процессов без переписывания методики

## Общий принцип

Скилл не содержит текущие приватные исходники smeta-vor-humanizer или smeta-pir, не знает их актуальные CLI-флаги и не объявляет готовой интеграцию с конкретным установленным валидатором. Перед первым профильным этапом родитель читает установленный owner skill, его исполняемые entrypoints и фактический `--help` нужных скриптов.

Подключаются существующие действия и проверки. Их код и аргументы фиксируются в небольшом каталоге capability. Каталог не генерируется из текста входящего документа. При необходимости короткий адаптер сначала рассматривается как отдельное изменение доверенного кода, проверяется и только после этого допускается в каталог следующего этапа.

Не превращай скрипт «всегда возвращает 0» в валидатор. Код выхода 0 допустим только при действительно успешной полной проверке требуемого свойства. Если текущий валидатор сигнализирует ошибки отчётом при нулевом exit code, нужен проверенный адаптер, который учитывает этот отчёт, или проверка остаётся за владельцем и этап не обозначается как полностью проверенный по данному свойству.

## ВОР / smeta-vor-humanizer

Основной скилл сохраняет владение классификацией строк, подготовкой формы, каноническим шаблоном, семантическим трассировщиком и правилами заполнения ссылок. Новый скилл координирует ограниченный участок, но не становится конкурирующим «главным сметным скиллом».

Подходящие узкие этапы: преобразовать уже извлечённые строки; подготовить рабочую копию известной операцией; проверить группу неоднозначных пар «исходник → результат». Для Jev передаются строка и необходимый контекст раздела/подраздела/чертежа, а не одно ключевое слово.

Утверждённые правила объёмов, единиц, марок, моделей, типов ресурсов, нумерации, связей ЛСР/ВОР, имён файлов, граф F/H/G/I, подписей и видимых границ таблицы не меняются. Модель не отменяет исходный структурированный тип «материал»/«оборудование» своей классификацией.

`same_numeric_tokens` сверяет только последовательность числовых токенов текста. Она не выявит замену единицы, неверное связывание строк, потерю технологии или перестановку одинаковых чисел. `json_fields_equal` проверяет только перечисленные верхнеуровневые поля JSON. Ни один из этих механизмов не заменяет профильный semantic tracer, XML/XLSX-валидацию или визуальную проверку.

Генерация выдаёт UTF-8 текст/JSON, а не бинарный XLSX/GGE/PDF. Бинарный результат создаёт существующий проверенный скрипт `command`. В `context` для Jev указывай заранее извлечённый текстовый промежуточный файл; не передавай двоичный PDF/DWG/XLSX как текст и не обрезай его молча до лимита.

## ПИР / smeta-pir

Подходящий этап: сопоставить уже сформулированный вывод с конкретным предоставленным фрагментом основания. Текст источника, область действия и условия применения передаются явно. Jev может указать supported/contradicts/insufficient, но не подбирает выдуманную норму и не признаёт всю смету корректной.

Обязательные математические и методические проверки существующего скилла сохраняются. НДС, специальные ставки, коэффициенты, округления и принятые пользователем правила не пересматриваются новым роутером.

## Программирование

Генеративное действие может подготовить патч как текст. Контроллер не исполняет и не импортирует полученный код. Применение патча к рабочей копии и запуск тестов — отдельный допущенный command-этап с существующим инструментом, явным scope и финальным просмотром сильной моделью. Нельзя зарегистрировать созданный worker скрипт как новый разрешённый исполнитель внутри текущего этапа.

Проверка JSON-формата или положительная оценка Jev не заменяет unit/integration tests, проверку зависимостей и содержательное ревью. Данный пакет не выдаёт разрешение на deploy, git push или изменение production.

## Память / GBrain

GBrain, reina-memory-context, USER/MEMORY, session_search и существующая память этим скиллом не перенастраиваются. Контекст проекта восстанавливает обычный процесс владельца. Не добавляй новую базу памяти, реестр долгосрочных решений или автоматическое обучение по неподтверждённым ответам Jev.

## Граница доверия внешних команд

Каталог фиксирует executable, прямые файловые аргументы и их хеши. Импортируемые библиотеки, вся транзитивная зависимость скрипта и поведение процесса этим не удостоверяются. Используй известное окружение и установленную изоляцию terminal. Не передавай каталог от недоверенного автора как «данные».

Команды запускаются без shell и без унаследованных API-ключей. Их HOME указывает на каталог текущего результата; stdout/stderr не передаются модели и не сохраняются контроллером. Скрипт, которому необходимы дополнительные рабочие файлы или отчёты, должен корректно работать в предоставленном `{workdir}`. Не требуй отключить ограничения ради несовместимой команды.

Основной артефакт каждого шага — ровно файл `output`. Побочные файлы внешнего инструмента не становятся автоматически проверенными deliverables. Их дополнительная приёмка остаётся у владельца; исходники не перезаписываются.
