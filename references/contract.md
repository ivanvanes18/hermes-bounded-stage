# Исполняемый контракт v1 и v2

Нормативная проверка формы реализована в `scripts/admission.py`. Ниже описан тот же интерфейс. Готовую карточку с реальными путями и SHA-256 создаёт автономный demo; не используй фиктивный хеш из примера вместо фактического.

## Карточка этапа

Верхний уровень — JSON-объект ровно с полями:

| Поле | Контракт |
|---|---|
| `schema_version` | Целое `1` или `2`, не boolean. `1` — поведение 1.0.0 без изменений; `2` дополнительно допускает действие `semantic_exception_filter` |
| `stage_id` | `[a-z][a-z0-9_-]{0,47}`; значение `none` зарезервировано |
| `goal` | Непустая цель, до 4000 символов |
| `constraints` | 0–16 непустых строк до 1000 символов; сами по себе не являются исполняемыми проверками |
| `inputs` | 1–8 именованных файлов: `{"path": "абсолютный путь", "sha256": "64 строчных hex-символа"}` |
| `steps` | 1–8 последовательных шагов |
| `limits` | `max_jev_calls`: 0–32; `max_generations`: 0–8; `max_seconds`: 1–3600, все целые |

Неизвестные поля отклоняются. Источники копируются в новый run и остаются связанными с оригинальными путями/хешами. Перед продолжением контроллер проверяет оригиналы, копии и все уже завершённые основные артефакты. Изменение источника требует новой карточки; не обновляй хеш в уже созданном run.

Каждый шаг содержит:

| Поле | Контракт |
|---|---|
| `id` | Уникальный идентификатор, не совпадающий с именем input или предыдущего шага |
| `output` | Только имя основного файла, до 120 символов, без `/`, `\`, начальной точки и управляющих символов |
| `context` | 1–8 различных имён inputs или **предыдущих** шагов; нет ссылок вперёд |
| `actions` | 1–8 допустимых действий |
| `selection` | Обязателен только при нескольких действиях; `instructions` и необязательные пороги |
| `checks` | 1–16 обязательных детерминированных проверок |
| `semantic_checks` | 0–8 проверок Jev: `id`, `instructions`, необязательные пороги |

Для разных имён шагов можно использовать одинаковое имя output: они сохраняются в разных каталогах. Основной артефакт: `RUN/artifacts/STEP_ID/OUTPUT`. Только он автоматически попадает в `completed`; побочные файлы команды не считаются автоматически проверенными.

## Действия

Каждое действие содержит `id`, `kind`, `description` и одно дополнительное поле:

| `kind` | Дополнительное поле | Исполнение |
|---|---|---|
| `copy` | `source`: имя из context | Создание точной копии, без LLM |
| `generate` | `instructions`: до 4000 символов | Однократный пакет для native worker; он возвращает UTF-8 текст/JSON |
| `command` | `capability`: имя каталога | Заранее допущенная команда, без shell |
| `semantic_exception_filter` | `source`: имя из context | Только `schema_version: 2`. Классификация готовых пар и сборка исключений |

При единственном действии Jev не вызывается для выбора. При нескольких она получает только допустимые `id` и описание, плюс автоматически добавленный `none`. Она не создаёт executable, argv, параметры, новые шаги или права.

## `semantic_exception_filter` (только schema_version 2)

Действие содержит `id`, `kind`, `description`, `source`, `instructions` и необязательные `required_flags`, `batch_size`, пороги. `source` — имя из context данного шага; это **входной артефакт готовых пар**, созданный допущенным производителем. Контроллер его не создаёт и не изменяет.

Артефакт читается **один раз** и целиком, с тем же лимитом 1 MiB, что и остальной JSON. Хешируется именно прочитанный буфер, сверяется с опечатанным хешем этого имени в run и разбирается тот же буфер — с обычным строгим отказом при повторяющихся ключах и NaN/Infinity. Классифицируются ровно те байты, которые прошли сверку: между хешированием и разбором нет второго обращения к пути, в которое можно подставить другое содержимое. После каждой партии путь перепроверяется снова; любое расхождение — `input_changed:ИМЯ` (или `output_changed:ИМЯ`, если источник — результат предыдущего шага) и остановка, а не продолжение.

```text
required_flags: 0–32 различных имени флага; все перечисленные должны быть true для covered
batch_size:     целое 1–32, по умолчанию 8 — сколько пар уходит в один вызов Jev
```

Артефакт — закрытый JSON ровно такой формы:

```json
{"schema_version": 2,
 "items": [{"item_id": "poz-1", "text": "…",
            "candidates": [{"candidate_id": "cand-1", "text": "…",
                            "flags": {"unit_matches": true, "quantity_matches": true}}]}]}
```

Ограничения: 1–256 items, 1–64 candidates на item, не более 512 пар всего, до 32 флагов на кандидата. `item_id`/`candidate_id` — те же идентификаторы `[a-z][a-z0-9_-]{0,47}`, уникальные (кандидаты — в пределах своей позиции). Значения флагов — строго boolean; отсутствие требуемого флага, лишнее поле, другой `schema_version` или нечисловой мусор блокируют шаг. Молчаливого усечения списка нет.

Jev получает только `item_id`, `candidate_id` и тексты партии — без флагов, без суммы, без других кандидатов. Вопрос на каждую пару фиксирован: ключ `ITEM_ID:CANDIDATE_ID`, варианты ровно `exact`, `partial`, `none`. Бюджет `max_jev_calls` резервируется целиком перед каждой партией: при нехватке шаг останавливается с `jev_budget_exhausted`, а не отправляет усечённую партию.

Решение складывает контроллер, а не модель:

| Условие (в этом порядке) | `status` | `reason` |
|---|---|---|
| Ответ ниже порогов | `exception` | `low_confidence` |
| `partial` | `exception` | `partial` |
| `none` | `missing` | `missing` |
| `exact`, но хотя бы один `required_flags` = false | `exception` | `deterministic_failed` |
| `exact` и все требуемые флаги true | `covered` | `null` |

Основной результат шага — закрытый JSON из трёх уровней: все пары, по одному решению на позицию и короткий список для владельца.

```json
{"schema_version": 2,
 "decisions": [{"item_id": "poz-1", "candidate_id": "cand-1", "match": "exact",
                "status": "covered", "reason": null, "confidence": 0.93,
                "probabilities": {"exact": 0.95, "partial": 0.04, "none": 0.01},
                "deterministic_flags": {"unit_matches": true, "quantity_matches": true}},
               {"item_id": "poz-1", "candidate_id": "cand-2", "match": "partial",
                "status": "exception", "reason": "partial", "confidence": 0.91,
                "probabilities": {"exact": 0.10, "partial": 0.88, "none": 0.02},
                "deterministic_flags": {"unit_matches": true, "quantity_matches": true}}],
 "item_decisions": [{"item_id": "poz-1", "candidate_id": "cand-1", "match": "exact",
                     "status": "covered", "reason": null, "confidence": 0.93,
                     "probabilities": {"exact": 0.95, "partial": 0.04, "none": 0.01},
                     "deterministic_flags": {"unit_matches": true, "quantity_matches": true}}],
 "exceptions": []}
```

`decisions` — канонический протокол разбора: **каждая** пара, включая отклонённые альтернативы. Каждая запись несёт принятый ответ целиком (`match`, `confidence`, полное распределение `probabilities`) и детерминированные флаги кандидата в том виде, как их подал производитель артефакта. Этого достаточно, чтобы владелец пересобрал `status` по таблице выше, не открывая `state.json` и не имея доступа к самому run. Флаги приводятся полностью, а не только требуемые: требуемые перечислены в опечатанной карточке.

`item_decisions` — ровно одна запись на `item_id`, в порядке артефакта. Кандидат выбирается по убыванию `p(exact) + 0.5 * p(partial)`; при равенстве баллов остаётся первый по порядку артефакта. Отбор ранжирует только уже поданных кандидатов: он ничего не создаёт и **не пересматривает** статус выбранной пары — запись целиком копируется из `decisions`. Балл любой пары воспроизводится из её же `probabilities`, поэтому выбор проверяем по самому файлу.

В `exceptions` попадает каждая запись `item_decisions` со статусом не `covered`, включая `missing` — то есть не более одной строки на позицию. Три отклонённых кандидата одной закрытой позиции не дают трёх поводов для разбора: они остаются доказательством в `decisions`. Сам `exceptions` намеренно остаётся коротким указателем — `item_id`, `candidate_id`, `reason`. Пара `(item_id, candidate_id)` уникальна по контракту артефакта, поэтому это однозначная ссылка; дублировать доказательства ещё раз не нужно и вредно — копии расходятся при любой ручной правке, и тогда неясно, какая из них протокол.

Позиция без покрытия видна именно в `exceptions`/`item_decisions`: пустой `decisions` контрактом артефакта невозможен, а позиция, у которой все кандидаты отклонены, всё равно даёт одну строку с её лучшим по баллу кандидатом и его фактическим статусом. В версии 1.1.0 политики, исключающей `missing` из обзора владельца, нет: результат всегда остаётся на стороне большего, а не меньшего контроля. Проверяй результат обычными детерминированными проверками (`json`, `json_has_keys` с `decisions`/`item_decisions`/`exceptions`) — сам факт записи файла проверкой не является.

Низкая уверенность и ложный детерминированный флаг дают исключение по конкретной паре, а этап продолжается: владелец получает полный список. Некорректный ответ Jev (другая модель, неизвестный вариант, неверное распределение, недобор ответов) — это `needs_review` / `jev_unavailable` для всего шага, и артефакт решений не создаётся вовсе. Состояния «часть пар принята по сломанному ответу» не существует.

## Детерминированные проверки

| `kind` | Дополнительные поля | Что реально проверяется |
|---|---|---|
| `nonempty` | Нет | Основной файл имеет хотя бы один байт |
| `json` | Нет | Строго разбираемый JSON; повторяющиеся ключи и NaN/Infinity отклоняются |
| `same_sha256` | `source` | Полное побайтовое совпадение с указанным источником |
| `same_numeric_tokens` | `source` | Равенство последовательности лексических числовых токенов UTF-8 текста |
| `json_has_keys` | `fields`: 1–32 имени | Верхний уровень — объект, перечисленные поля присутствуют |
| `json_fields_equal` | `source`, `fields` | Перечисленные верхнеуровневые поля равны исходнику при строгой JSON-сериализации; `"12"`, `12`, `12.0` различаются |
| `command` | `capability` | Завершение заранее проверенного внешнего валидатора с exit 0; основной output не изменён валидатором |

Источники проверок должны присутствовать в context данного шага. Для внешнего валидатора полнота проверки зависит от самого валидатора и корректности адаптера. Нулевой exit code не доказывает правильность непроверенных свойств.

Контроллер фиксирует хеш проверяемого output и проверяет его неизменность после валидации и ответа Jev. Исходники и предыдущие результаты также перепроверяются. Не существует состояния «валидатор отклонил, но Jev разрешила».

## Вопросы Jev и пороги

В этой версии используется только `Choice`; Noul и Score намеренно не добавлены. Для смысловых проверок варианты фиксированы: `supported`, `contradicts`, `insufficient`. Для `semantic_exception_filter` — ровно `exact`, `partial`, `none`. Все независимые вопросы проверки одного результата отправляются вместе; выбор действия и проверка ещё не созданного результата не объединяются.

Стартовые пороги:

```json
{"min_probability": 0.90, "min_confidence": 0.80, "min_margin": 0.20}
```

Их можно явно задать в selection или конкретной semantic_check. Значения должны быть конечными числами 0–1. `min_margin` — разница между вероятностью выбранного варианта и следующей наибольшей вероятностью.

Эти пороги **не откалиброваны на русскоязычных сметах пользователя** и не означают гарантированную точность. Не понижай их по ходу этапа, чтобы получить зелёный результат. Изменение политики требует новой согласованной карточки и проверки на известных случаях.

Модель зафиксирована как `jev-1.13.0`. Ответ другой модели, неверный тип ответа, неполный набор ответов/вариантов, NaN, неверная сумма вероятностей или выбор не максимального варианта отклоняются. Нет скрытого переключения на latest, preview или другого провайдера.

## Каталог команд

Верхний уровень: `schema_version: 1`, `capabilities: {...}`. Без каталога доступны copy/generate и встроенные проверки. Допускается до 16 возможностей.

Каждая capability содержит ровно:

```text
role: action | check
argv: массив отдельных строк, executable обязательно абсолютный
pins: {каждый абсолютный файловый аргумент argv: его SHA-256}
timeout_seconds: целое 1–120
```

Подстановки разрешены только целым аргументом: `{ref:ИМЯ}` — файл из context, `{output}` — основной результат, `{workdir}` — его рабочий каталог. `{output}` обязателен. Подстановка внутри строки не поддерживается. Прямые абсолютные аргументы предназначены для executable/скриптов и должны существовать и иметь pin. Пути источников и результатов задавай подстановками.

Shell-интерпретаторы и `-c` не допускаются. Команда с ролью check не может использоваться как action, и наоборот. При изменении executable/скрипта этап блокируется. Сами команды — доверенный код, который может иметь произвольное поведение вне контроллера; это не механизм безопасного исполнения чужих программ.

Запуск происходит в текущем terminal backend, не в обход него. Команде передаётся минимальное окружение без пользовательских API-ключей. Время процесса ограничено меньшим из timeout_seconds и остатка этапа. После завершения/тайм-аута контроллер завершает оставшуюся группу процесса. Умышленно убежавший из группы процесс не является поддерживаемым сценарием изоляции.

## Ограничения данных и HTTP

Один обычный файл — до 64 MiB. Один UTF-8 фрагмент и суммарный context для генерации/оценки — до 64 KiB. Карточка/состояние JSON читаются с лимитом 1 MiB. HTTP request/response — до 128 KiB. Превышение лимита блокирует этап: молчаливого усечения нет.

TypeSafe вызывается только по фиксированному HTTPS endpoint с ключом из `TYPESAFE_API_KEY`. Редиректы, proxy-переменные окружения и автоматические повторы не используются. HTTP исполняется в отдельном процессе с ограничением до 15 секунд и оставшимся временем этапа. Необходимый корпоративный proxy этой версией не поддерживается; не обходи сетевую политику.

`--allow-typesafe` существует только у init и синтетического smoke. Advance/submit не умеют самостоятельно расширять разрешение. Контекст, инструкции вопроса и варианты отправляются во внешний API; разрешение пользователя должно покрывать весь этот набор, а не только исходный файл.

## Пакет генерации

Контроллер создаёт `packets/NONCE.json`, возвращает абсолютные packet_path/submission_path и ждёт файл `inbox/NONCE.txt`. Пакет содержит цель, ограничения, реальные текстовые источники, инструкции, stage_id/step_id/nonce и точный выходной путь.

При submit nonce должен совпасть с текущим ожиданием. Пакет и входы сверяются заново. Результат копируется в основной output и проходит те же проверки, что обычная команда. Повторная отправка использованного nonce не выполняет шаг второй раз.

Не называй генерацию проверенной только потому, что worker вернул правдоподобный текст. Не заменяй пакет своим JSON с флагом `passed`.

## Статусы, сбои и доказательства

| Status | Exit | Значение |
|---|---:|---|
| `ready` | 0 | Новый run создан; этап ещё не выполнен |
| `awaiting_generation` | 10 | Требуется конкретный результат worker, это не ошибка |
| `ready_for_parent_review` | 0 | Все перечисленные шаги/проверки завершены; нужна приёмка владельца |
| `needs_review` | 20 | Этап остановлен; возможны частичные результаты; автоматического продолжения нет |
| `blocked` | 2 | Команда/контракт неприемлемы; не означает успешную проверку |

`executing` — внутреннее write-ahead состояние. Если новый процесс увидел его после прерывания, возвращается interrupted_execution, а действие не запускается повторно. Блокировка run через flock запрещает два одновременных продвижения.

`report.json` содержит `skill_version`, `plan_schema_version`, пути и хеши основных артефактов, исполненные проверки, выбранные action_id, счётчики и границы измерений. Подробности принятых ответов Jev есть в state.json; тела запросов, секреты и stdout/stderr команд туда не записываются. Источники и пакеты генерации локально содержат рабочие данные — защищай и храни run как клиентские файлы.

`jev_calls` считает зарезервированные попытки, включая попытки, которые не дошли до API из-за отсутствия ключа. Usage отражает только полученные и принятые ответы. `generations` считает пакеты контроллера, не все вызовы модели Hermes. Полной финансовой статистики здесь нет.

Хеши, порядок шагов и nonce защищают от штатной рассинхронизации/случайного повторения, но не удостоверяют историю перед процессом, способным переписать весь run. Неподконтрольный worker с теми же файловыми правами может обойти любой пользовательский скрипт. Реальная изоляция — задача Hermes/ОС, а достаточность проверок — задача владельца.


## Staged 1.2 addendum: отдельный executor protocol

Описанные выше планы v1/v2 и native delegation сохранены. Новый `route-*` путь имеет отдельные schemas/runtime/state; см. [executor-routing.md](executor-routing.md). Он не меняет global/delegation model и не запускает весь process skill внутри worker. Родитель фиксирует methodology и принимает результат, executor выполняет только один packet. Новая bounded correction не меняет старую v1/v2 retry policy.
